# OCR 质量基线与优化结论

审阅日期：2026-09-18  
需求标识：`PX-OCR-QUALITY-01`  
关联路线：`docs/reviews/2026-09-18-pixpin-feature-gap-roadmap.md`

## 结论

当前 PP-OCRv6 small + EdgeGNN 增强链在已有 14 张同源合成图上明显优于 Clippy 的 Tesseract
fallback，特别是双栏、旋转和中文场景；简单单行两者都能完全识别。这个结论只适用于已记录的合成
样本，不能外推为真实截图、中日混排、公式或所有设备上的总体精度。

2026-09-21 又加入 4 张由 Firefox 实际栅格化的自有 UI 基线，覆盖暗色设置页、代码与斜体、票据
表格和 2400 px 长文档。它比 Pillow 文字图更接近应用截图，但仍是受控页面，不代表相机、手写、
任意网站或总体用户数据。增强链在该语料上继续优于 Tesseract，同时暴露了暗色空白、代码框和表格
阅读顺序问题；其中表格排序已用纯几何规则修复并保存前后对照。

`EdgeGNN` 不是图像边缘增强。它以文字框为节点、相邻关系为边，预测哪些行属于同一段；字符是否
识别正确主要由 det 框、原像素透视 crop、rec 模型、字典和 CTC 决定。Clippy 自研 XY-cut 负责组的
阅读顺序。历史证据还显示 EdgeGNN 会把同一段的普通相邻行拆成 singleton，导致 `result.text` 在每行
之间插入空白行；本轮增加了保守的视觉段落合并来修复这一问题。

## 同源 A/B

14 张图片由原生成脚本重新生成，逐张 SHA-256 与 2026-09-12 增强链证据完全一致。本轮修改前，
`pipeline.py`、`edge_features.py`、`layout_groups.py` 等运行文件的 SHA 也与该次增强链运行一致；随后
`pipeline.py` 只在 Edge 输出后加入视觉段落合并，A/B 使用的检测框、逐行文字、crop、rec 和 CTC
行为没有改变，完整文件 SHA 因该有意改动不再相同。Tesseract 使用当前
`/usr/bin/tesseract 5.5.0` 和产品相同的 `eng+chi_sim` 参数重新运行。比较文本按阅读顺序以 LF 连接，
指标按 Unicode code point 计算。

| 指标 | PP-OCRv6 small + EdgeGNN | Tesseract 5.5.0 |
|---|---:|---:|
| 原始 CER | **0.34%** | 32.70% |
| 去空白 CER | **0.00%** | 30.98% |
| 空白 precision | **1.000** | 0.779 |
| 空白 recall | **0.980** | 0.751 |
| 空白 F1 | **0.990** | 0.765 |
| 14 图总耗时 | 8.56 s | **3.60 s** |

增强链约慢 2.38 倍。Tesseract 的主要失分来自双栏按行交错、8°/-11° 旋转漏字，以及中文字符间
插入空格和少量汉字错误。增强链 13/14 图非空白字符完全正确；唯一混合中文样本的非空白 CER 为 0，
但模型删除了“项目记录 2026 年 9 月”“金额明细 100.00 元”“AABB 112233”中的视觉空格，导致该图
原始 CER 8.05%。因此“增强链更好”与“空格问题已经解决”不能混为一谈。

逐图输入 SHA、期望文本、两引擎输出、指标、时间和运行文件 SHA 保存在
`docs/reviews/evidence/2026-09-18-ocr-ab/ab-results.json`。

## 新 v1 语料的双引擎基线

本轮新增 5 张可再分发合成图，使用仓库内 OFL Noto Sans CJK SC 生成，并以 SHA 固定：

- 中英日混排、连续空格、重复字母/数字、货币；
- 数值、全半角标点和常用数学符号；
- 双栏阅读顺序；
- 公式路由与 LaTeX 真值；
- 低对比小字。

当前 Tesseract 在这组 v1 smoke corpus 上的原始 CER 为 27.47%，去空白 CER 19.53%，空白 F1
0.673；它不提供结构化行框、阅读顺序或公式，因此这些能力记录为 `supported=false`，不会用一个
虚构整图框计为失败。预测和报告分别保存在同一 evidence 目录的
`tesseract-predictions.json`、`tesseract-report.json`。

本轮按 `requirements.lock` 建立 Python 3.12.14 隔离环境，使用仓库锁定的公开 PP-OCRv6 small
det/rec/字典，以及用户已有并自行核权的 EdgeGNN 模型，在同一 corpus 重跑当前增强链。结果如下：

| 指标 | PP-OCRv6 small + EdgeGNN | Tesseract 5.5.0 |
|---|---:|---:|
| 检测 Hmean | **1.000**（12 TP，0 FP/FN） | 不支持 |
| 阅读顺序错误率 | **0.000**（11 对） | 不支持 |
| 原始 CER | **13.30%** | 27.47% |
| 去空白 CER | **1.18%** | 19.53% |
| 空白 precision / recall / F1 | 1.000 / 0.561 / **0.719** | 0.776 / 0.594 / 0.673 |
| P50 / P95 | 340.74 / 373.97 ms | **226.61 / 292.48 ms** |
| 结构化公式 | 不支持 | 不支持 |

增强链的 12 个框全部命中，双栏顺序无倒置。169 个非空白真值码点只有 2 次替换，均为 Unicode
兼容字形差异：`∑→Σ` 和 `Δ→∆`；复制结果仍保留模型原始码点，评测不会用规范化隐藏差异。31 次
原始编辑中有 25 次为空白漏失，模型会把大部分连续双空格压成单空格，并在
`±0.02  √2≈1.414` 等符号边界漏空格。公式样本只能输出线性 `x²+1/2=√2`，没有恢复二维结构，
所以仍明确记为 `structuredFormula=false`。

增强预测、完整分层报告和去除绝对路径/耗时后的 CTC 发射证据保存在同一 evidence 目录的
`v1-enhanced-predictions.json`、`v1-enhanced-report.json`、`v1-ctc-emissions.json`。模型 SHA、
运行库版本和参与采集的源码 SHA 一并写入发射证据；模型文件和 Edge 权重不进入仓库。

## 可选英语空白复识别

PaddleOCR 官方说明 `en_PP-OCRv5_mobile_rec` 针对英语空格漏识别做了优化。本轮用固定官方 ONNX
进行逐框 A/B，并采用保守融合合同：通用模型先识别；只有该行全部非空白字符都在英语字典中，且
英语结果的非空白 Unicode 序列与通用结果逐码点完全相同、空白数量更多、置信度仍过线时才替换。
这会拒绝 `¥→#`、`∑↔Σ`、`Δ↔∆` 等看似相近但码点不同的候选。

| 语料 / 管线 | 原始 CER | 去空白 CER | 空白 recall / F1 | P50 / P95 |
|---|---:|---:|---:|---:|
| 混合 v1 / 通用 | 13.30% | 1.18% | 0.561 / 0.719 | 340.74 / 373.97 ms |
| 混合 v1 / 英语空白档 | **11.16%** | 1.18% | **0.649 / 0.787** | 786.31 / 923.18 ms |
| 英语空白 v1 / 通用 | 9.93% | 1.87% | 0.647 / 0.786 | 545.65 / 592.94 ms |
| 英语空白 v1 / 英语空白档 | **8.51%** | 1.87% | **0.706 / 0.828** | 687.00 / 704.02 ms |

它在混合 v1 中补回 5 个空格，在专项 6 图中补回 2 个空格，去空白 CER 保持不变；专项样本的
序列号与线性公式改善，货币、重复标识符和源码没有被改写。代价是在混合 v1 上 P50 增加 131%，
且模型仍不能恢复多数连续双空格。因此该模型作为 `setup_models.py --english-spacing` 的可选质量档，
不替换默认通用链。专项生成器、6 张固定 SHA 图片以及两管线预测/报告均已入库；证据文件名以
`english-spacing-` 和 `v1-english-spacing-` 开头。

## 可选文字行方向分类

PaddleOCR 官方文字行方向模块只区分 0°与 180°。Clippy 先用检测框几何把高窄 crop 固定旋成横行，
再用固定版本 `PP-LCNet_x0_25_textline_ori` 判断是否翻转 180°，因此同一逐框链覆盖整图
0°/90°/180°/270°。分类分数低于 0.8 时不翻转；返回框始终保留原图坐标。

固定四向语料使用同一行“方向 OCR 90° SN-A1”旋转生成，4 张图片、真值框与 SHA 均入库：

| 管线 | 检测 Hmean | 原始 / 去空白 CER | 完全正确 case | P50 / P95 |
|---|---:|---:|---:|---:|
| 通用几何旋转 | 1.000 | 43.75% / 46.15% | 2 / 4 | 538.14 / 558.67 ms |
| 可选方向模型 | 1.000 | **0% / 0%** | **4 / 4** | 548.17 / 678.84 ms |

无方向模型时 0°和90°正确，180°误成短片段，270°低于接受阈值；启用后四向文字完全一致。
这证明逐框方向合同和当前合成样本有效，不能外推到真实拍照、弯曲文字或竖排语言版式。预测和报告
保存为 `orientation-generic-*` 与 `orientation-model-*`；权重不进入仓库。

## PP-OCRv6 small / medium 分阶段 A/B

本轮新增 4 张 UI 压力图，覆盖暗色界面、1.25x/1.5x/2x 缩放、小字号、低质量 JPEG 往返、
中英日、易混淆 `00Il1lO0`、代码、货币和表格式数值。它们仍是可再生成的合成 UI，不冒充真实用户
截图。固定官方 medium det 为 62,032,837 bytes，medium rec 为 76,554,979 bytes；后者超过产品当前
单模型 64 MiB 上限。A/B 每个 case 均走一次独立 sidecar 进程，包含模型加载时间；采集器同时记录
该进程自己的峰值驻留内存。下表 RSS 是本次 Linux x86_64 同机运行的最大 `VmHWM`，包含 Python、
OpenCV、ONNX Runtime、模型和工作区，适合比较档位，不表示嵌入应用后的增量内存。

| 语料 / det+rec | 检测 Hmean | 原始 / 去空白 CER | 空白 F1 | P50 / P95 | 峰值 RSS |
|---|---:|---:|---:|---:|---:|
| 混合 v1 / small+small | 1.000 | **13.30%** / **1.18%** | 0.719 | **341 / 376 ms** | **193 MiB** |
| 混合 v1 / medium det | 1.000 | 12.02% / 1.78% | **0.774** | 625 / 742 ms | 271 MiB |
| 混合 v1 / medium rec | 1.000 | 15.02% / **1.18%** | 0.659 | 594 / 715 ms | 264 MiB |
| 混合 v1 / medium+medium | 1.000 | 15.02% / **1.18%** | 0.659 | 921 / 1,043 ms | 346 MiB |
| 英语空白 v1 / small+small | 1.000 | 9.93% / 1.87% | 0.786 | **294 / 339 ms** | **167 MiB** |
| 英语空白 v1 / medium rec | 1.000 | **7.09% / 0%** | **0.828** | 508 / 535 ms | 247 MiB |
| UI 压力 v1 / small+small | **1.000** | **19.00%** / 1.42% | **0.596** | **369 / 384 ms** | **191 MiB** |
| UI 压力 v1 / medium det | 0.714 | 20.33% / 1.42% | 0.509 | 704 / 751 ms | 316 MiB |
| UI 压力 v1 / medium rec | **1.000** | 20.00% / **0.94%** | 0.545 | 686 / 719 ms | 261 MiB |
| UI 压力 v1 / medium+medium | 0.714 | 20.67% / **0.47%** | 0.486 | 982 / 1,065 ms | 379 MiB |

medium rec 在英语专项消除了 `ll/II` 非空白错误，也在暗色样本把 `日本语` 改回 `日本語`，但混合
语料和 UI 压力语料的原始 CER、空白 F1 都回退。medium det 在干净公式框上恢复了线性空格，并把
表格整行拆成单元格；同基线排序修复后金额次序已正确，但 UI 压力语料的空白 F1 仍由 0.596 降至
0.509，峰值 RSS 由 191 MiB 升至 316 MiB。medium+medium 在该语料达到 379 MiB，约为 small 的
1.98 倍。因此 medium 不能作为 small 的直接替换，也不能通过提高 64 MiB 文件上限就称为质量升级。
默认链继续使用 small；cell/row 双层真值只证明表格顺序可恢复，不抵消文字、空白与资源回退。

研究采集器 `model_tier_ab.py` 只接受上述两个固定官方 SHA，生成临时 `researchModelProfile` manifest。
Rust 产品 manifest 的 `deny_unknown_fields` 会拒绝该字段，所以研究档位不会成为隐藏产品入口。全部
预测、分标签报告和无本机路径的环境身份保存在 `2026-09-18-ocr-model-tiers/`。

## 表格 row/cell 双层合同与同基线排序

普通行框 Hmean 会把“整行检测”和“拆成多个 cell”视为互斥答案，无法判断表格是否仍能正确复制。
本轮为固定 `table-values` 图片增加独立 `table-corpus-v1`：真值保存 table、row、cell、列序号和
原图四边形；评测器分别计算 raw cell 检测、按纯几何聚合后的 row 检测、产品原始 reading order，
以及按 y 行/x 列重建后的文本。评测重建不参与产品推理。

| 管线 | row Hmean | cell Hmean | raw inversion | raw / 几何非空白 CER |
|---|---:|---:|---:|---:|
| small det + small rec | 1.000 | 0.000 | 0 / 3 | 0% / 0% |
| medium det + small rec（修复前） | 1.000 | 0.632 | 1 / 21 | 17.39% / 0% |
| medium det + small rec（修复后） | 1.000 | 0.632 | **0 / 21** | **0% / 0%** |

medium 检出的第三行三个框本来已包含完整字符，但 `¥88.00` 的顶边比左侧 `日本茶 3` 低约 2px；
旧排序先比较精确 y，导致金额跑到行首。`layout_groups.py` 现在把半个中位行高内的框视为同一基线，
先按 x、再按 y 排序。真实 sidecar 使用相同 medium det、small rec 和 Edge 权重重跑后，输出恢复为
`日本茶 3 → ¥88.00 → ¥264.00`；检测框、字符、row/cell 指标均未改变。前后预测、报告和运行源码
SHA 保存在 `2026-09-18-ocr-table-order/`。

cell Hmean 0.632 不表示 medium 比 small 的表格文字更差：表头仍是整行框，前两列也有合框，因此只
命中 12 个 cell 真值中的 6 个。当前修复只保证可复制的 row-major 文本，不声称已经恢复可导出的
电子表格结构；空单元格、跨行/跨列、无边框复杂表格仍需更大语料和独立结构模型。

## Firefox 栅格化 UI 语料与规则表格排序

`browser-ui-v1` 的源 HTML、文字和布局属于 Clippy 仓库，字体沿用 OFL-1.1 Noto Sans CJK SC。
Firefox 155.0.1 在 DPR 1 下捕获 4 张固定 PNG；`capture.json` 同时绑定源 HTML、字体、捕获脚本、
宿主、视口、逐图 SHA/尺寸和真值数量。普通测试只运行 `capture.py --verify`，不会因浏览器升级自动
重写图片。采集器和评测 CLI 共用严格资产读取器，拒绝路径逃逸、任一路径分量的符号链接、非普通
文件、超预算文件、PNG chunk/CRC 错误、尺寸漂移和 SHA 不符。

同机 Tesseract 5.5.0 与 PP-OCRv6 small + EdgeGNN 使用完全相同的 4 张输入。增强链使用临时隔离
Python 3.14.4 环境；公开 det/rec/字典与用户本地 Edge 权重均按固定 SHA 核对，路径和权重没有进入
仓库。整体结果如下：

| 指标 | Tesseract 5.5.0 | 增强链（表格排序前） | 增强链（当前） |
|---|---:|---:|---:|
| 检测 Hmean | 不支持 | 0.881（78 TP / 11 FP / 10 FN） | 0.881（相同框） |
| 阅读顺序错误率 | 不支持 | 10.46%（91 / 870） | **1.03%（9 / 870）** |
| 原始 CER | 30.14% | 20.92% | **13.86%** |
| 去空白 CER | 23.42% | 17.10% | **8.91%** |
| 空白 F1 | 0.658 | **0.777** | **0.777** |
| P50 / P95 | 1,033 / 1,199 ms | 1,004 / 2,934 ms | 959 / 2,692 ms |
| 峰值 RSS | **110 MiB** | 483 MiB | 485 MiB |

前后增强运行是两次独立进程采集，约 45 ms P50 与 2 MiB 峰值差异属于单次运行波动，不能归因于
几何排序。真正受代码改变的只有输出顺序：检测框、识别文字、空白 F1 和模型资产保持相同。当前
增强链的峰值 RSS 约为 Tesseract 4.4 倍，长图 P95 仍接近 2.7 s，不能只用 CER 宣称无成本升级。

表格场景有 16 个 cell 和 4 个 row，增强链检测 Hmean 均为 1.0；旧 XY-cut 看到贯通列 gutter 后
按列输出，造成 36 / 120 对倒置，表格标签去空白 CER 66.18%。新规则只有在至少 3 条基线各含至少
3 个框，且这些密集行覆盖至少一半候选时才采用行优先；普通双栏继续列优先。重跑后表格倒置为 0，
表格标签去空白 CER 为 0.48%。独立表格评测只按框几何重建时仍为 1% CER，说明剩余一处是字符
错误，不是排序错误。

分层结果仍有明确边界：长图去空白 CER 为 0.34%、空白 F1 为 0.902；斜体标签为 5.19% / 0.831。
代码标签虽比 Tesseract 的去空白 CER 21.57% 改善到 17.78%，空白 F1 却从 0.750 降到 0.672；暗色
设置页去空白 CER 从 45.05% 改善到 37.39%，空白 F1 从 0.563 降到 0.494，并保留 9 次阅读顺序
倒置。当前规则没有用 OCR 文字、表格关键词或真值掩盖这些回退；两引擎预测、修复前后报告和无绝对
路径的环境哈希均保存在 `docs/reviews/evidence/2026-09-21-ocr-real-ui/`。

## 本轮实现

1. `quality-corpus.schema.json` 固定图片相对路径、SHA、尺寸、许可、标签、框、原始文字、顺序与公式；
2. `quality-predictions.schema.json` 区分整段文本、行框和结构化公式能力；
3. `quality_metrics.py` 计算四边形检测 Hmean、原始/去空白 CER、精确 Unicode 空白 F1、整行匹配、
   阅读顺序 inversion、公式支持/完全匹配和性能；
4. `quality_collect.py` 用产品相同参数采集 Tesseract，或通过固定 manifest 采集增强 sidecar，并以
   Linux `VmHWM`、macOS RSS 采样或 Windows `PeakWorkingSetSize` 记录每次独立进程的峰值内存；
5. `quality-fixtures/v1/` 保存生成器、5 张固定 PNG 和人工真值；
6. 本地门禁加入不依赖模型/第三方 wheel 的质量合同与视觉段落测试；
7. 增强链在 EdgeGNN 分组后合并“同栏、正常行距、近似字号”的相邻片段；大段距、跨栏回跳、
   并排文字和字号突变仍保持边界。历史 singleton 证据重放后，两段文本恢复为 3+3 行，双栏恢复为
   左 3 行 + 右 3 行，已有正确分组保持不变。
8. `--diagnostics-dir` 为每个 case 在全新私有目录写入有界诊断；逐字符证据包含 class、发射时间步、
   前置 blank-run 和相邻发射间距，总计最多 4096 个发射。普通产品请求不构造或返回这些对象。
9. `table-corpus-v1` 与 `quality_table.py` 将 cell、聚合 row、原始顺序和几何可恢复性分开计分；
   同基线稳定排序只使用框几何，不读取 OCR 文字或表格真值。

## 后续优化顺序

### 1. 空格与重复字符

当前字典含 ASCII space，但 greedy CTC 只保留模型实际发出的空格类别；字典覆盖不能修复模型漏空格。
本轮诊断确认缺失的 `2→√` 空格前有较长 blank-run，但中日文字形本身也普遍产生较长 blank，且
连续双空格通常只发出一个 space class，单靠时间步无法可靠还原空格数量。因此当前不增加阈值补空格
规则。后续规则只能作用于有充足语料证明的拉丁/数字/符号边界，并用连续空格、中文、日文、代码、
序列号和金额分层验收；不能在汉字之间普遍插空格。重复字符必须保留 blank 分隔证据，不能用词典
纠错改写编号。

英语专用模型 A/B 已完成并以上述不改非空白码点的合同可选接入。下一步需要增加真实 UI、代码、
终端、比例字体和压缩截图，判断新增空白是否仍保持 precision=1；在证据扩大前不放宽到基于置信度
选择不同字符，也不对中英日混排行做分段重识别。

### 2. 方向与裁切

可选官方文字行方向模型已经接入，并与 H48 识别 crop 共用总像素预算和统一 deadline。没有采用
四方向文字识别置信度竞赛：CTC 分数跨错误方向不可校准，且会将逐框识别成本放大四倍。下一步扩充
真实 UI 的倒置/旋转截图及细小竖框，检查 0.8 阈值的误翻转率；文档去畸变只在真实拍照语料进入
范围后评估，普通截图不承担其包体和延迟。

### 3. 检测与模型档位

det 漏框、错误合框和 rec 错字已按阶段初测，证明 medium 的内部公开指标不能直接外推到 Clippy。
下一步增加真实 UI、斜体、日文、表格和长图来源样本，并为表格单独定义 cell/row 层级；只替换目标
阶段，不能用总 CER 掩盖检测粒度或阅读顺序退化。当前已有 Linux peak RSS；Windows/macOS CPU 与
峰值内存仍须在相同模型和语料上重跑，不能用 Linux 结果替代。

### 4. 公式

普通 OCR 只能得到线性字符，无法恢复分数、上下标、根式和矩阵结构；medium rec 对固定公式仍只是
`x²+1/2=√2`，没有结构提升。公式区域需要独立检测/路由到 PP-FormulaNet 或 UniMERNet，并输出
LaTeX/MathML；当前通用模型一律报告 `structuredFormula=false`。官方 PP-FormulaNet-S 已约 224 MB，
官方 CPU 参考耗时约 254 ms，明显超出当前 OCR 资产预算，第一阶段只能作为显式可选组件并单独设计
下载、许可、内存和失败回退。

### 5. EdgeGNN 与阅读顺序

保留 EdgeGNN 的模型输出和视觉合并前后分组，分别评测 paragraph membership 与最终阅读顺序。
本轮视觉合并只修正常行距 singleton；阈值、颜色特征或模型替换必须在标题、列表、表格、双栏、
跨栏标题和真实 UI 上验证，不能因为文字 CER 不变就认为版面没有回退。
