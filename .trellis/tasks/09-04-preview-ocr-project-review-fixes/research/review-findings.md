# Review findings — 2026-09-04

## Confirmed defects

1. `src/js/preview/content-renderers.js` 在 `getClipImage`、`getConfig` 和 `ocrAvailable` 等异步边界后没有统一的渲染代次校验；旧图片请求可以向新条目的共享 DOM 写入图片、尺寸、错误或 OCR。
2. `src/js/preview-panel.js` 的 `ensureLibs` 分支在等待依赖后没有校验当前 clip；首次加载依赖时存在旧文本覆盖新条目的竞态。
3. 前端先调用 `ocr_available`，`recognize` 内又重新解析并探测 Tesseract；每次未缓存图片会产生重复进程探测。
4. `ocr_image` 仅检查持久缓存，没有进行中请求合并或并发上限；快速切换和多消费者可能重复执行同一 OCR。
5. 可编辑 PNG 的 iTXt 写入、读取与恢复后端仍在，但主界面入口移除后没有可达的工程重开路径。复制图片进入剪贴板会经 arboard 得到 RGBA 并重新编码，不能保留 PNG iTXt。
6. 图片 watcher 每 500 ms 获取并扫描完整 RGBA。该轮询性能风险尚未由本任务证明为实际回归，但输入缺少尺寸、像素和字节预算，是确定的内存/编码安全边界缺口。
7. 首版路径缓存实现持有同步锁执行 `tesseract --version`，会把其它可用性查询和安装后的缓存失效一起阻塞；必须把子进程探测移出临界区，并防止旧代次结果回写。
8. 异常剪贴板图片只清除 RGBA 指纹时，上一张合法图片的 PNG 哈希仍会短路后续入库；两个去重层级都必须失效。
9. 原生拖放事件订阅初始化失败时，先创建的隐藏覆盖层会成为不可达 DOM；失败路径必须同步清理。

## Decisions

- 预览采用单调递增 render generation，不依赖 DOM 是否碰巧仍存在来判断请求有效性。
- OCR 后端保持 CLI 子进程方案；缓存可执行路径、限制并发并按 clip ID 合并请求。
- 工程重开采用仅在拖放期间出现的入口，不改变主窗口常态布局；只接受包含有效 Clippy 工程元数据的单个 PNG。
- 图片预算只拒绝异常/超限输入，不对合法图片降采样。
- OCR 缓存写入失败只影响持久化，不把已经成功的识别改成失败；预览与翻译入口保持相同语义。
